The Problem

Why Does JPMS Even Exist?

For over two decades, Java developers lived with the classpath — a flat list of JARs loaded into a single namespace. It worked, but it came with deep structural problems that grew worse as codebases scaled. JPMS (Java Platform Module System) was Java's answer, years in the making.

JAR Hell

Multiple versions of the same class on the classpath. The JVM silently picks one — usually the wrong one. NoSuchMethodError at runtime, not compile time.

Runtime Crash
No Real Encapsulation

public classes are accessible from anywhere on the classpath — even "internal" implementation classes you never meant to expose. There is no way to hide them.

No Boundary
Split Packages

Two JARs can define classes in the same package. The classloader picks one JAR per package — creating unpredictable, hard-to-debug splits.

Undefined Behaviour
Monolithic JDK

Every Java app carried the entire JDK (~200MB+) even if it only used java.util. No way to ship a minimal runtime for microservices or IoT.

Bloated Runtime
Hidden Dependencies

The classpath doesn't tell you what a library depends on — it just loads everything. Circular deps, missing transitive deps — discovered only at runtime.

Implicit Contract
Security Exposure

Sun's internal APIs (sun.misc.Unsafe, etc.) were accessible to any code. Breaking internal JDK details became mainstream, blocking JDK upgrades.

Security Risk
How JPMS Solves All of These
JPMS introduces a module — a named, self-describing unit of code that explicitly declares: what it exports (public API), what it requires (dependencies), and optionally what it opens for reflection. The JVM enforces these boundaries at both compile time and runtime.
Strong Encapsulation

Non-exported packages are invisible to other modules — not just by convention, but enforced by the JVM itself.

Explicit Dependencies

Every dependency is declared in module-info.java. Missing deps fail at JVM startup — not buried in a stack trace at 3am.

Scalable Packaging

Use jlink to bundle only the modules your app needs — create a custom JRE as small as ~30MB.

Core Concepts

JPMS Building Blocks

Master these 8 concepts and you understand 90% of the module system.

1. The Module

A module is a named, self-describing collection of packages and resources. Defined by a module-info.java file at the root of the module's source tree. Think of it as a "super-JAR" with an explicit identity and contract.

Analogy
If a JAR is a box of goods, a Module is that box with a manifest on the outside listing exactly what's inside, what it needs delivered to function, and what it will share with its neighbours.
module-info.javaModule Declaration
// Placed at: src/com.raghavan.booklib/module-info.java

module com.raghavan.booklib {

    // What this module exports (public API)
    exports com.raghavan.library.model;
    exports com.raghavan.library.service;

    // com.raghavan.library.internal is NOT listed
    // = COMPLETELY HIDDEN from outside world
}
2. exports & requires

exports — declares which packages of this module are accessible to other modules. Only exported packages are visible.

requires — declares that this module depends on another. The JVM validates this at startup and refuses to run if deps are missing.

  • exports pkg Makes a package's public types visible to all other modules
  • exports pkg to X Qualified export — only visible to module X
  • requires M This module needs module M to compile and run
  • requires transitive M This + any module requiring this also gets M
module-info.javaexports + requires
module com.raghavan.catalog {

    // Explicit dependency on booklib
    requires com.raghavan.booklib;

    // Public API exposed by this module
    exports com.raghavan.catalog.api;

    // Qualified export (only to app module)
    exports com.raghavan.catalog.debug
        to com.raghavan.app;

    // impl package: NOT exported = hidden
}

module com.raghavan.app {
    requires com.raghavan.catalog;
    requires com.raghavan.booklib;
    // requires java.base; // implicit always
}
3. opens & Reflection

Even if a package is exported, deep reflection (accessing private fields/methods) is blocked by JPMS. The opens directive grants reflective access — critical for frameworks like Spring, Hibernate, and Jackson that use reflection heavily.

Spring Boot Reality
Spring's DI, AOP proxies, and @Autowired all rely on reflection. Without opens, Spring throws InaccessibleObjectException.
module-info.javaopens for Reflection
module com.raghavan.myapp {
    requires spring.context;
    requires spring.beans;
    requires spring.boot;
    requires spring.boot.autoconfigure;

    // Open packages for Spring's reflection
    opens com.raghavan.myapp
        to spring.core;

    opens com.raghavan.myapp.model
        to spring.core, jackson.databind;

    // opens pkg; // opens to ALL modules (broad)
    // open module { ... } // opens everything

    exports com.raghavan.myapp.api;
}
4. uses & provides (SPI)

JPMS integrates with Java's Service Provider Interface (SPI) via uses and provides. This enables a consumer module to declare it uses a service, and a provider module to supply an implementation — without the consumer knowing the implementation class.

This is the foundation of pluggable architecture: JDBC drivers, logging frameworks (SLF4J), and codec libraries all use this pattern.

module-info.javaSPI: uses + provides
// Consumer module: knows the interface
module com.raghavan.app {
    requires com.raghavan.booklib;
    // Declares it uses a BookFormatter service
    uses com.raghavan.library.service.BookFormatter;
}

// Provider module: supplies the implementation
module com.raghavan.csv.formatter {
    requires com.raghavan.booklib;
    // Declares it provides the implementation
    provides com.raghavan.library.service.BookFormatter
        with com.raghavan.csv.CsvBookFormatter;
}

// Consumer loads at runtime via ServiceLoader:
// ServiceLoader.load(BookFormatter.class)
//   .findFirst().get().format(book);
Classification

The Four Types of Modules

Not all modules are created equal. JPMS distinguishes four kinds based on how they're packaged and loaded.

Named Module
Explicit

Has a module-info.java. Lives on the module path. Strong encapsulation enforced. The goal state.

// module-info.java
module com.myapp {
  exports com.myapp.api;
}
Automatic Module
Migration Aid

Plain JAR (no module-info) placed on the module path. Gets an auto-generated name from JAR filename. Exports all packages. Transition tool.

// guava-31.1.jar on module-path
// becomes: com.google.guava
// ALL packages exported
// ALL modules accessible
Unnamed Module
Legacy / Classpath

Any JAR on the classpath (not module path). Forms a single unnamed module. Can read all named modules but named modules can't require it. Legacy compatibility.

// java -cp lib/*.jar App
// All classpath = unnamed module
// Can read named modules
// Named can't require this
Platform Module
JDK Built-in

The 75+ modules that make up the JDK itself (java.base, java.sql, java.logging, etc.). java.base is always present — never needs to be declared.

// java.base is auto-required
// Others need explicit requires:
requires java.sql;
requires java.logging;
Which Type Should I Use?
New greenfield project? Always use Named Modules.
Third-party library dependency? Most are Automatic Modules until they ship a module-info.
Legacy code on classpath? Unnamed Module — still works, zero migration needed initially.
JDK types (List, Map, etc.)? Platform Modules — java.base always included.
Reference

module-info.java Complete Reference

Every directive you can use in a module declaration, with examples.

exports

Makes a package's public types accessible to other modules. Only packages listed in exports are visible — all others are completely hidden.

  • exports pkg All modules can access public types in pkg
  • exports pkg to M Qualified — only module M can access pkg
Important
Even if a class is public, if its package is not exported, it's inaccessible from other modules. Accessibility in JPMS = public AND in exported package.
module-info.javaexports examples
module com.raghavan.booklib {

    // Unqualified: all modules can see this
    exports com.raghavan.library.model;
    exports com.raghavan.library.service;

    // Qualified: ONLY the app module can see this
    exports com.raghavan.library.admin
        to com.raghavan.app;

    // Multiple qualified targets
    exports com.raghavan.library.metrics
        to com.raghavan.monitoring,
           com.raghavan.admin;

    // NOT listed = INVISIBLE:
    // com.raghavan.library.internal
    // com.raghavan.library.cache
}
requires

Declares that this module depends on another. The JVM resolves all requires declarations at startup and fails immediately if any module is missing — no more runtime surprises.

  • requires M

    Normal dependency. This module reads M's exported packages.

  • requires transitive M

    This module AND any module requiring THIS module can also read M. (Implied readability)

  • requires static M

    Compile-time-only dependency. Optional at runtime. Useful for annotation processors.

module-info.javarequires variants
module com.raghavan.catalog {

    // Simple: catalog needs booklib
    requires com.raghavan.booklib;

    // Transitive: anyone requiring catalog
    // also automatically gets java.logging
    requires transitive java.logging;

    // Static: only needed at compile time
    // (e.g. annotation processor, optional lib)
    requires static org.checkerframework.checker;

    // java.base is ALWAYS implicitly required
    // No need to write: requires java.base;

    exports com.raghavan.catalog.api;
}
Fail-Fast Guarantee
If com.raghavan.booklib is absent from the module path, the JVM prints a clear error at startup and refuses to run — before any code executes.
opens

Even with a package exported, deep reflection (accessing private fields/methods via setAccessible(true)) is blocked by default. The opens directive grants reflective access.

module-info.javaopens for Spring/Hibernate
module com.raghavan.webapp {
    requires spring.context;
    requires spring.beans;
    requires com.fasterxml.jackson.databind;

    // Spring needs to inject fields via reflection
    opens com.raghavan.webapp.service
        to spring.beans, spring.context;

    // Jackson needs to serialize/deserialize
    opens com.raghavan.webapp.dto
        to com.fasterxml.jackson.databind;

    // Open module = opens ALL packages to ALL
    // (escape hatch, not recommended long-term)
    // open module com.raghavan.webapp { ... }

    exports com.raghavan.webapp.api;
}
uses & provides (SPI)

JPMS makes the Java Service Provider Interface (SPI) first-class. This is the same mechanism powering JDBC drivers, logging frameworks, and pluggable codecs — now type-safe and module-verified.

+------------------+ +-------------------+ | consumer module | | provider module | | | | | | uses | | provides | | BookFormatter; | | BookFormatter | | | | with | | // loads via: | | CsvFormatter; | | ServiceLoader | | | | .load( | | (impl hidden in | | BookFormatter) | | non-exported pkg)| +------------------+ +-------------------+ | | +-------MODULE PATH--------+
JavaSPI Usage in Code
// Service interface (in booklib module)
public interface BookFormatter {
    String format(Book book);
}

// Consumer uses ServiceLoader
public class ReportGenerator {
    public void generateReport(List<Book> books) {
        ServiceLoader<BookFormatter> loader =
            ServiceLoader.load(BookFormatter.class);

        BookFormatter formatter = loader
            .findFirst()
            .orElseThrow(() -> new RuntimeException(
                "No BookFormatter found!"));

        books.forEach(b ->
            System.out.println(formatter.format(b)));
    }
}

    exports com.raghavan.megaapp.api;
    exports com.raghavan.megaapp.model;

    exports com.raghavan.megaapp.internal.admin

    opens com.raghavan.megaapp.service
        to spring.beans, spring.context;

    // Allow Jackson to serialize DTOs
    opens com.raghavan.megaapp.dto
        to com.fasterxml.jackson.databind;

    // Open to ALL (testing, scripting)
    opens com.raghavan.megaapp.test.helpers;

    uses com.raghavan.library.service.BookFormatter;
    uses java.sql.Driver; // JDBC driver discovery

    provides com.raghavan.library.service.BookFormatter

public class Book {
    private final String isbn;
    private final String title;
    private final String author;
    private final int year;

        this.isbn   = isbn;
        this.title  = title;
        this.author = author;
        this.year   = year;

    public String getTitle()  { return title; }
    public String getAuthor() { return author; }
    public int getYear()      { return year; }

    @Override
    public String toString() {

    }
}
Javacom/raghavan/library/BookRepository.java
package com.raghavan.library;

import java.util.*;

/**
 * This class is intended to be INTERNAL to the library package.
 * Without JPMS, there is NOTHING stopping external code from
 * importing and instantiating this class directly.
 *
 * This is the core encapsulation problem JPMS solves.
 */
public class BookRepository {           // <-- "public" leaks this everywhere
    private final List<Book> store = new ArrayList<>();

    public void save(Book book) {
        store.add(book);
    }

    public Optional<Book> findByIsbn(String isbn) {
        return store.stream()
                     .filter(b -> b.getIsbn().equals(isbn))
                     .findFirst();
    }

    public List<Book> findAll() {
        return List.copyOf(store);
    }
}
The Problem Illustrated
BookRepository is a persistence implementation detail. The library author wants only the service layer to use it. But because Java's access control operates at the package level (not module level), any class anywhere on the classpath can import com.raghavan.library.BookRepository and use it.
Javacom/raghavan/catalog/CatalogService.java
package com.raghavan.catalog;

import com.raghavan.library.Book;
import com.raghavan.library.BookRepository;  // Accessing "internal" class directly!
import java.util.List;

public class CatalogService {
    // Directly couples to internal BookRepository implementation
    // Should be using an interface/abstraction, but nothing enforces it
    private final BookRepository repository = new BookRepository();

    public void addBook(String isbn, String title, String author, int year) {
        repository.save(new Book(isbn, title, author, year));
    }

    public List<Book> listAll() {
        return repository.findAll();
    }

    public void printCatalog() {
        System.out.println("=== Book Catalog (No Modules) ===");
        listAll().forEach(b -> System.out.println("  " + b));
        if (listAll().isEmpty())
            System.out.println("  (empty catalog)");
    }
}

package com.raghavan.library.internal;  // 'internal' package — NOT exported in module-info

import com.raghavan.library.model.Book;
import com.raghavan.library.service.BookService;
import java.util.*;

/**
 * INTERNAL implementation — NOT exported by module-info.java.
 *
 * This class is INVISIBLE outside the com.raghavan.booklib module.
 * Even though it is 'public', the module system overrides visibility.
 *
 * Outside modules CANNOT:
 *   - Import this class
 *   - Instantiate it
 *   - Extend it
 *   - Access it via reflection (without 'opens' directive)
 *
 * This is JPMS strong encapsulation in action.
 */
public class InMemoryBookRepository implements BookService {
    private final Map<String, Book> store = new LinkedHashMap<>();

    @Override
    public void addBook(Book book) {
        store.put(book.getIsbn(), book);
    }

    @Override
    public Optional<Book> findByIsbn(String isbn) {
        return Optional.ofNullable(store.get(isbn));
    }

    @Override
    public List<Book> findAll() {
        return List.copyOf(store.values());
    }
}

Analysis

Pros & Cons of JPMS

An honest assessment for a senior Java developer adopting JPMS in 2026.

Advantages
  • Strong Encapsulation
    Non-exported packages are invisible at both compile and runtime. No more accidentally depending on implementation details.
  • Explicit Dependency Graph
    module-info.java is machine-readable architecture documentation. Tools can visualize your entire dependency graph.
  • Fail-Fast Startup
    Missing modules cause immediate JVM failure before any code runs. No more 3am NoClassDefFoundError in production.
  • jlink — Custom Runtime Images
    Bundle only what your app needs. A Spring Boot service can ship with a ~50MB JRE instead of 300MB JDK.
  • First-Class SPI
    uses/provides directives make Service Loader patterns type-safe and module-verified.
  • No Circular Dependencies
    Circular requires is a compile error — forces clean layered architecture.
  • JDK Itself Is Modularized
    Java's own runtime is split into 75+ modules. java.base, java.sql, java.logging etc. — pick what you need.
Challenges
  • Steep Learning Curve
    New concepts (module path vs classpath, unnamed vs automatic vs named), cryptic error messages, unfamiliar --add-opens flags.
  • Framework Friction
    Spring Boot, Hibernate, Jackson all use reflection. You'll need multiple opens directives to make DI/serialization work.
  • Ecosystem Still Catching Up
    Many popular libraries still don't ship module-info.java. You'll use Automatic Modules (which have weaker guarantees).
  • Build Tool Complexity
    Maven/Gradle module configurations are complex. Multi-module builds require careful plugin configuration.
  • Migration Cost
    Migrating a large legacy codebase to JPMS is a significant investment. Bottom-up migration required (leaf modules first).
  • opens Defeats Encapsulation
    Frameworks requiring broad opens (Spring's open module pattern) undermines the very encapsulation JPMS provides.
  • No Version Resolution
    JPMS doesn't solve JAR versioning conflicts. You still need Maven/Gradle for dependency version management.
Raghavan's Pragmatic Take (for Enterprise Spring Boot Development)

For a new greenfield Spring Boot 3+ microservice in 2026: JPMS with open module is the pragmatic choice — you get the architectural documentation and startup fail-fast, without fighting every framework. Reserve strict named module exports for pure-Java libraries and shared domain modules where encapsulation really matters. For existing production services: leave on classpath unless you have a compelling jlink or security reason to migrate.

open module vs opens
open module M { ... } — opens ALL packages for reflection. Simplest approach for Spring Boot.
module M { opens pkg to X; } — surgical, explicit, more secure. Better long-term goal.
Start with open module, migrate to explicit opens as you understand your reflection surface.

package com.raghavan.bookvault.controller;

import com.raghavan.bookvault.model.Book;
import com.raghavan.bookvault.service.BookService;
import jakarta.validation.Valid;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.*;
import java.net.URI;
import java.util.List;

@RestController
@RequestMapping("/api/v1/books")
public class BookController {

    private final BookService bookService;

    public BookController(BookService bookService) {
        this.bookService = bookService;
    }

    @GetMapping
    public List<Book> getAllBooks() {
        return bookService.findAll();
    }

    @GetMapping("/{isbn}")
    public ResponseEntity<Book> getByIsbn(@PathVariable String isbn) {
        return bookService.findByIsbn(isbn)
                          .map(ResponseEntity::ok)
                          .orElse(ResponseEntity.notFound().build());
    }

    @PostMapping
    public ResponseEntity<Book> createBook(@Valid @RequestBody Book book) {
        Book saved = bookService.save(book);
        URI location = URI.create("/api/v1/books/" + saved.getIsbn());
        return ResponseEntity.created(location).body(saved);
    }

    @DeleteMapping("/{isbn}")
    public ResponseEntity<Void> deleteBook(@PathVariable String isbn) {
        bookService.deleteByIsbn(isbn);
        return ResponseEntity.noContent().build();
    }
}

Migration

Migrating to JPMS — Step by Step

Bottom-up migration strategy: start from leaf modules, work up to the app module.

Step 1
Audit Dependencies
Run jdeps --module-deps myapp.jar to find what JDK modules your code actually uses. Fix any use of deprecated internal APIs (sun.*, com.sun.*).
Step 2
Check Third-Party Libraries
Identify which dependencies ship a module-info.java (Named Modules) vs which are Automatic Modules. Note: Automatic Module names are unstable.
Step 3
Start with Leaf Modules
Add module-info.java to pure domain/utility modules first — those with no Spring/framework deps. Get these Named Modules compiling cleanly.
Step 4
Work Upwards Through Layers
Add module-info.java to service/repository layers. Use open module for Spring Boot service modules initially.
Step 5
Tighten Opens Directives
Replace open module with specific opens pkg to framework; directives. Run integration tests to confirm nothing breaks.
Step 6
Explore jlink
Once all modules are Named, use jlink to create minimal runtime images for Docker deployments. Measure image size reduction.

Common Migration Pitfalls
  • Split packages — two modules cannot export the same package. Refactor first.
  • Cyclic requires — A→B→A is a compile error. Break cycles with interfaces.
  • Automatic Module name instability — Automatic Module names can change when the library adds a real module-info.
  • Reflection failures — InaccessibleObjectException at runtime means you need opens.

Best Practices

JPMS Best Practices

Hard-won lessons from production Java module system adoption.

Convention: Module name = the root package of the module's exported API.
// ✅ Good — module name matches root package
module com.raghavan.booklib {
    exports com.raghavan.booklib.api;
}

// ❌ Bad — misleading or generic names
module booklib { ... }      // no reverse-domain
module utils { ... }        // too generic
module com.company.v1 { ... } // version in name
This convention makes module names globally unique and self-documenting.

Export only interface/contract packages. Keep implementation packages unexported. Use a Factory or ServiceLoader to provide implementations to consumers. 
// ✅ Good — API vs impl separation
module com.raghavan.booklib {
    exports com.raghavan.booklib.api;     // interface here
    // impl package NOT exported
}

// ❌ Bad — exposing implementation details
module com.raghavan.booklib {
    exports com.raghavan.booklib.api;
    exports com.raghavan.booklib.impl; // leaks implementation!
}

Start with open module for quick wins, but work towards explicit opens pkg to framework; over time. This minimizes the reflection surface and maximizes security. 
// Phase 1 (migration): broad
open module com.raghavan.webapp { ... }

// Phase 2 (hardened): surgical
module com.raghavan.webapp {
    opens com.raghavan.webapp.model
        to com.fasterxml.jackson.databind;
    opens com.raghavan.webapp.service
        to spring.beans, spring.context;
}

requires transitive is powerful — it propagates readability to all callers. But overusing it creates invisible transitive dependencies, undermining the explicit dependency goal of JPMS.
  • Use requires transitive M only when your exported API returns or accepts types from M
  • If your API doesn't expose types from M, use plain requires M

If you publish libraries, add Automatic-Module-Name to your MANIFEST.MF even before you add a full module-info.java. This reserves your module name and lets consumers safely require your library by name. 
<!-- In pom.xml maven-jar-plugin config -->
<archive>
  <manifestEntries>
    <Automatic-Module-Name>com.raghavan.booklib</Automatic-Module-Name>
  </manifestEntries>
</archive>

--add-opens and --add-exports on the JVM command line are migration escape hatches, not permanent solutions. They bypass JPMS encapsulation entirely. Track each one as a tech debt item and resolve it by:
  • Adding proper opens directives to module-info.java
  • Upgrading the offending library that accesses internal APIs
  • Refactoring to avoid the reflection that triggers it

Scenario 1: The Broken Build

You add module-info.java to your app and immediately get: error: package org.springframework.context is not visible

Diagnosis & Fix: You forgot to add requires spring.context; in your module-info. The Spring JARs are on the module path (named/automatic modules) but your module hasn't declared a dependency on them. Add the missing requires directive.

Scenario 2: Runtime Crash

App compiles cleanly. At startup, Spring throws: InaccessibleObjectException: Unable to make field private String ... accessible

Diagnosis & Fix: Spring is trying to inject a private field via reflection but your module doesn't open that package. Add opens com.myapp.service to spring.beans, spring.context; or use open module for full Spring compatibility.

Scenario 3: jlink Failure

jlink --add-modules com.myapp fails with: Error: Module guava not found

Diagnosis & Fix: jlink only works with Named Modules — not Automatic Modules. guava doesn't have a module-info.java. Solutions: (a) Find a module-info-equipped version of guava, (b) Remove the guava dependency, (c) Create a module descriptor using moditect-maven-plugin.

Scenario 4: Circular Dependency

error: cyclic dependence involving com.myapp.service and com.myapp.model

Diagnosis & Fix: Two modules require each other — a circular dependency. JPMS forbids this. Fix by: (a) Extracting shared types into a third module both depend on, (b) Merging the two modules into one, (c) Inverting the dependency using interfaces/events.
