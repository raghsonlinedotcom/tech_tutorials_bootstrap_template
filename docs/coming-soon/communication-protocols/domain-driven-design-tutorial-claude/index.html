Core DDD Concepts

Definition: An object with unique identity that is tracked through its lifecycle.

Key Characteristics:

  • Has a unique identifier (ID)
  • Mutable - can change over time
  • Identity remains constant
  • Equality based on ID, not attributes

Example: Order, Customer, Product

Real-world analogy: Think of a person - they have a unique identity (SSN) and their attributes (name, address) can change, but they're still the same person.

Definition: Immutable object defined entirely by its attributes.

Key Characteristics:

  • No unique identifier
  • Immutable - cannot change after creation
  • Equality based on all attributes
  • Can be freely shared and replaced

Example: Money, Address, DateRange, Email

Best Practice: Use Value Objects to encapsulate validation logic and make your domain model more expressive.

Definition: A cluster of domain objects treated as a single unit with one root entity.

Key Characteristics:

  • Has one Aggregate Root (entry point)
  • Enforces consistency boundaries
  • External objects can only reference the root
  • Saved/loaded as a complete unit

Example: Order (root) contains OrderItem entities

Important: Keep aggregates small. Large aggregates can cause performance and concurrency issues.

Definition: Abstraction that provides collection-like interface for accessing domain objects.

Key Characteristics:

  • Hides persistence details
  • One repository per Aggregate Root
  • Defined as interface in Domain layer
  • Implemented in Infrastructure layer

Example: OrderRepository with methods like save(), findById()

Isolation: Repositories protect domain logic from persistence concerns, allowing technology changes without domain modifications.

Definition: Stateless service that contains domain logic not belonging to a specific entity.

When to Use:

  • Logic involves multiple aggregates
  • Logic doesn't naturally fit in any entity
  • Complex calculations or algorithms

Example: PricingService, InventoryService

Definition: Something that happened in the domain that domain experts care about.

Key Characteristics:

  • Named in past tense (OrderCreated, PaymentProcessed)
  • Immutable once created
  • Contains relevant data about what happened
  • Enables loose coupling between services

Example: OrderCreatedEvent, CustomerRegisteredEvent

Benefits: Events enable reactive architectures, audit trails, and eventual consistency across microservices.

Implementation Guide

Domain Layer Implementation

The heart of your application - contains business logic and rules.

Order.java (Aggregate Root) 
public class Order {
    private OrderId orderId;
    private String customerId;
    private List<OrderItem> items;
    private OrderStatus status;
    private Money totalAmount;
    
    public void confirm() {
        if (status != OrderStatus.PENDING) {
            throw new IllegalStateException(
                "Only pending orders can be confirmed"
            );
        }
        this.status = OrderStatus.CONFIRMED;
    }
    
    public void cancel() {
        if (status == OrderStatus.SHIPPED) {
            throw new IllegalStateException(
                "Cannot cancel shipped orders"
            );
        }
        this.status = OrderStatus.CANCELLED;
    }
}
Money.java (Value Object) 
public class Money {
    private final BigDecimal amount;
    private final String currency;
    
    public Money(BigDecimal amount, String currency) {
        if (amount.compareTo(BigDecimal.ZERO) < 0) {
            throw new IllegalArgumentException(
                "Amount must be positive"
            );
        }
        this.amount = amount;
        this.currency = currency;
    }
    
    public Money add(Money other) {
        if (!this.currency.equals(other.currency)) {
            throw new IllegalArgumentException(
                "Currency mismatch"
            );
        }
        return new Money(
            this.amount.add(other.amount), 
            this.currency
        );
    }
}
Key Point: Business rules live in the domain objects, not in services!

Application Layer Implementation

Orchestrates use cases and coordinates domain objects.

OrderApplicationService.java 
@Service
public class OrderApplicationService {
    
    private final OrderRepository orderRepository;
    private final KafkaEventPublisher eventPublisher;
    
    @Transactional
    public OrderResponse createOrder(CreateOrderRequest request) {
        // 1. Map DTO to domain objects
        List<OrderItem> items = request.getItems().stream()
            .map(item -> new OrderItem(
                item.getProductId(),
                item.getQuantity(),
                new Money(item.getUnitPrice(), "USD")
            ))
            .collect(Collectors.toList());
        
        // 2. Create domain object (business logic here)
        Order order = new Order(request.getCustomerId(), items);
        
        // 3. Persist
        Order savedOrder = orderRepository.save(order);
        
        // 4. Publish event
        OrderCreatedEvent event = new OrderCreatedEvent(
            savedOrder.getOrderId().getValue(),
            savedOrder.getCustomerId(),
            savedOrder.getTotalAmount().getAmount().toString()
        );
        eventPublisher.publishOrderCreated(event);
        
        // 5. Return response
        return toResponse(savedOrder);
    }
}
Application services are thin orchestrators - they delegate to domain objects for business logic.

Infrastructure Layer Implementation

Technical implementations for persistence, messaging, etc.

MongoDB Repository 
@Repository
public class OrderMongoRepository 
    implements OrderRepository {
    
    private final MongoTemplate mongoTemplate;
    
    @Override
    public Order save(Order order) {
        OrderDocument doc = toDocument(order);
        mongoTemplate.save(doc);
        return order;
    }
    
    @Override
    public Optional<Order> findById(OrderId id) {
        OrderDocument doc = mongoTemplate
            .findById(id.getValue(), 
                     OrderDocument.class);
        return Optional.ofNullable(doc)
            .map(this::toDomain);
    }
}
Kafka Publisher 
@Component
public class KafkaEventPublisher {
    
    private final KafkaTemplate<String, String> 
        kafkaTemplate;
    private final ObjectMapper objectMapper;
    
    public void publishOrderCreated(
        OrderCreatedEvent event) {
        try {
            String message = objectMapper
                .writeValueAsString(event);
            kafkaTemplate.send(
                "order-events", 
                event.getOrderId(), 
                message
            );
        } catch (Exception e) {
            throw new RuntimeException(
                "Failed to publish event", e
            );
        }
    }
}

Presentation Layer - REST Controllers

HTTP endpoints for external clients.

OrderController.java 
@RestController
@RequestMapping("/api/orders")
public class OrderController {
    
    private final OrderApplicationService orderService;
    
    @PostMapping
    public ResponseEntity<OrderResponse> createOrder(
        @RequestBody CreateOrderRequest request) {
        OrderResponse response = orderService.createOrder(request);
        return ResponseEntity.status(HttpStatus.CREATED).body(response);
    }
    
    @GetMapping("/{orderId}")
    public ResponseEntity<OrderResponse> getOrder(
        @PathVariable String orderId) {
        OrderResponse response = orderService.getOrder(orderId);
        return ResponseEntity.ok(response);
    }
    
    @PutMapping("/{orderId}/confirm")
    public ResponseEntity<OrderResponse> confirmOrder(
        @PathVariable String orderId) {
        OrderResponse response = orderService.confirmOrder(orderId);
        return ResponseEntity.ok(response);
    }
    
    @DeleteMapping("/{orderId}")
    public ResponseEntity<Void> deleteOrder(
        @PathVariable String orderId) {
        orderService.deleteOrder(orderId);
        return ResponseEntity.noContent().build();
    }
}

Best Practices & Tips

Do's
  • ✓ Keep aggregates small
  • ✓ Use Value Objects for validation
  • ✓ Make domain models rich in behavior
  • ✓ Use domain events for decoupling
  • ✓ Test domain logic thoroughly
Don'ts
  • ✗ Don't create anemic domain models
  • ✗ Don't put business logic in services
  • ✗ Don't create large aggregates
  • ✗ Don't expose internal state
  • ✗ Don't skip validation
Tips
  • 💡 Use ubiquitous language
  • 💡 Model behaviors, not data
  • 💡 Start with bounded contexts
  • 💡 Iterate and refine
  • 💡 Collaborate with domain experts
